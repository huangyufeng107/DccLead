1. 目标与方案边界

1.1 建设目标

  1. 智能信息采集：AI外呼系统将自动识别、消歧并确认四项必填信息——车系、门店、日期和时段。
  2. 对话预校验（Pre-fetch 0ms）：当系统采集到门店和日期后，会提前拉取可用时段信息。用户在表达时段需求时，系统将基于本地缓存即时判断，确保对话过程流畅高效。
  3. 通话中意向锁定与随路交付：四项信息收集完整且经用户口头确认后，AI 在通话结束挂机时，将“外呼结果标签 + 试驾四要素 + 沟通事实录音小结”一次性随路打包交付 DCC 培育系统。
  4. DCC 自主即时裁决与中台合并下发：DCC 作为唯一业务中枢，独掌建单与流转决策权。接收到随路数据包后即时裁决：意向达标且要素齐全直接生成正式试驾工单并推送 NEV 中台直达店端；要素缺失或转人工则生成跟进线索，零废单产生，彻底防范外部系统不确定性风险。
  5. 无份额兜底机制：若在 DCC 最终校验时目标时段已无试驾份额，系统自动生成试驾线索推送至 NEV 线索中台，由对应专营店主动联系用户协调时间。
架构决策（方案 B）：废除原“通话中即时预建工单 + 通话后标签校验作废”的两阶段过度机制。外呼系统专注于交互与数据提炼，通话中不向 DCC 发起建单调用；DCC 在收到挂机完整数据包后掌握 100% 裁决权，从源头杜绝废单与状态不一致风险。

4. 核心业务规则

4.1 四项信息采集

字段是否必填AI 处理规则
车系必填通过同义词映射标准车系；多候选时追问确认。
门店必填按城市、门店别名和用户口述消歧；多候选时确认。
日期必填将相对时间转为标准日期；用户修改日期后允许重新查询。
时段必填映射至门店标准时段；用户修改时段后在缓存数据中即时判断。

4.2 Pre-fetch 规则

  • 触发：采集到门店 + 日期后，AI 调用 DCC 可用性查询接口，取得该日可用时段。
  • 使用：用户提供时段时，AI 在当前通话 Session 中完成即时判断；变更车系、门店或日期时允许重新拉取。
  • 边界：缓存数据只用于对话引导，不做资源锁定、不扣减份额、不对用户承诺预约成功。

6.1 AI 对话流畅度监控方案：业务口径与轻量落地

一、 背景与目标：为什么要监控这个指标？

在 AI 打电话帮客户查询“可预约时段”时，查询响应速度直接决定了客户的通话体验：

  • 业务痛点：如果 AI 后台查询慢，客户在电话里就会遇到明显停顿，感知到“AI 冷场、发呆”，甚至失去耐心直接挂断电话；
  • 核心目标：彻底杜绝 AI 交互卡顿，确保语音对答像真人销售顾问一样即时、自然、流畅；
  • 极简实现原则：不搞复杂昂贵的三方全链路时钟对时，直接复用 DCC 现有的“试驾可用性查询”基础服务，每次查询完成时顺手记录一条服务端耗时日志即可。

二、 技术实现规则：数据怎么收集与分档？（技术操作与打捞口径）

这是提供给技术研发团队的操作规范，明确日志记录什么、怎么计算去重与分档：

维度分类 核心记录字段（通俗人话） 业务用途与防错规则
1. 谁在查（身份标识） 通话会话 ID（call_session_id）、线索 ID（lead_id）、单次查询流水号（query_id） 以 call_session_id + query_id 唯一去重，确保一次时段查询只算一次，不产生重复统计。
2. 查什么（业务上下文） 预约门店、预约日期、意向时段，以及客户是否改了日期（date_changed） 用于识别客户在通话过程中是首次查询，还是临时改期发起的重新拉取。
3. 查了多久（服务端耗时） 服务接收时间（request_at）、返回 AI 时间（response_at）、总耗时毫秒数（response_ms），以及是否命中缓存（cache_hit） 统一由 DCC 单一服务端打点计算（response_ms = response_at - request_at），彻底规避跨系统时钟偏差。
4. 查的结果（调用状态） 有可用时段 / 无可用时段 / 查询超时 / 系统异常，及错误码与重试次数 确保慢响应、超时和失败均可精准追溯，不能因失败而从分母中脱落。

📊 耗时分档聚合规则（公平统计，三档互斥加和 = 100%）：

    • 🟢 0–50ms（即时响应 · 秒回）：必须同时满足“耗时 ≤ 50ms 且命中缓存（cache_hit = true）”，即 AI 预加载完成后的“完全秒回”，客户毫无等待感；
    • 🟡 50–200ms（轻量校验）：眨眼级的轻微核实，人类耳朵与大脑听觉上感知不到任何卡顿；
    • 🔴 > 200ms（明显停顿 · 慢响应）：通话中会出现半秒左右的迟疑，属于技术团队需要重点排查和消灭的异常情况。
