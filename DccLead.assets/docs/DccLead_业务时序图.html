SEQ-001 · 多渠道线索接入、下发审核与 7 维度规则引擎派单时序 线索流入与分配

展示三无忧冷线索、天网集客与线下批次文件接入 DCC 接入网关，经排重校验与下发审核入库，联动【任务排班】读取在线坐席负荷配额，触发【培育策略】7 维度规则引擎匹配，最终通过 WebSocket 实时派单至【培育任务】坐席工作台的端到端调用闭环。

对应原型：【线索管理】➔【三无忧/下发审核】+【培育策略】➔【线索分配规则】 参与方：5 个泳道 消息数：15 条交互 重点：分布式排它锁 · 幂等落库 · 负荷配额熔断
同步/异步请求 (Request) 业务响应 (Response) 消息事件 (Event / MQ) 异常/拒绝分支 (Error / Rejected)
# 发送方 接收方 消息 / 接口调用 类型 触发条件 技术实现约束
1 上游数据源 (三无忧/天网) 【线索管理】服务 POST /api/leads/sync/batch (批量下发名单) request 每天凌晨定时批处理或业务手动同步推单 请求体包含批次号 batchNo、签名 sign、加密线索数组
2 【线索管理】服务 DCC 数据库 INSERT INTO dcc_lead (状态: 待审核/待分配) request 批次签名校验合法且批次号未处理过 手机号唯一排重索引，30 天重复线索自动合并老潜客档案
3 DCC 数据库 【线索管理】服务 返回受影响行数与排重过滤统计 response 数据库操作完成 记录插入数、更新数、跳过数，形成入库对账流水
4 【线索管理】服务 上游数据源 HTTP 200 OK (包含接收总数与受理批次ID) response 数据安全持久化后立即响应 不等待后续耗时分配逻辑，避免外部网关超时
5 【线索管理】服务 【培育策略】规则引擎 发布 MQ 消息 topic: dcc_lead_alloc_event event 【下发审核】人工/自动审核通过 使用 RocketMQ 顺序消费，携带批次 ID 与白名单门店标签
6-7 【培育策略】规则引擎 DCC 数据库 查询在线坐席、班次日历、当前分配负荷与规则配置 request 分配引擎开始计算 联动【任务排班】，只选取状态为 ONLINE 且未达单日上限坐席
8a 【培育策略】规则引擎 DCC 数据库 更新线索为“待分配公海”，写入告警日志 error 无符合条件的在线坐席或全部坐席满负荷 触发站内信和企业微信通知班长，提示增加在岗排班
8b-10 【培育策略】规则引擎 DCC 数据库 加锁更新 dcc_lead.owner_id 并写入分配历史 request 匹配到 7 维度加权最优坐席 Redis 分布式锁 lock:seat:${agentId}，防止并发超配
11-13 【线索管理】服务 【培育任务】工作台 (UI) WebSocket 发送事件 LEAD_ALLOCATED event 事务落库成功 前端监听到事件后无刷新向【我的任务】顶部追加卡片并播放提示音
架构一致性说明：多渠道线索接入采用“先落库持久化、即时应答上游、异步排队分配”的削峰填谷模式。分配计算失败不影响线索的物理存储，未分配线索自动保存在公海池中，班长可通过工作台随时一键重分配。
SEQ-002 · AI 智能外呼任务下发、机器人通话与话单回执时序 AI外呼与通信

定义排程任务触发、向第三方 AI 外呼引擎 (AliCti) 下发名单、机器人拨打意向识别、Webhook 异步接收话单、回写通话记录与触发未接通波次重呼的端到端调用时序。

对应原型：【培育策略】➔【AI外呼配置】+【统计报表】➔【AI试驾排程效能看板】 参与方：5 个泳道 消息数：15 条交互 重点：Webhook 签名防刷 · 话单幂等性 · A/B级高意向直派人工
# 发送方 接收方 消息 / 接口调用 类型 触发条件 技术实现约束
1 【培育策略】调度中心 DCC 接入网关 检查外呼时间窗口与可用坐席阈值 request 定时排程触发 (如每天 09:30) 非工作时段禁止外呼，若可用坐席低于阈值自动挂起任务
2-3 DCC 接入网关 AI外呼引擎 POST /task/create (提交名单与模板) request 批次名单检查通过 接口传 enterpriseId、customerClidsGroup、名单数组
4 AI外呼引擎 DCC 接入网关 返回 JSON { code: 0, taskId: "TASK-8910" } response 供应商受理成功 记录外部 taskId 并绑定到本地外呼批次
5-6 AI外呼引擎 潜客电话 线路呼叫与双向音频流建立 event 调度发起拨打 机器人语音对答，实时提取意向关键词与意图标签
7 AI外呼引擎 DCC 接入网关 POST /webhook/call-result (通话话单推送) event 通话挂机后 3 秒内推送 携带 callId、duration、recordUrl、intentGrade (A/B/C/D/N)
8-9 DCC 接入网关 DCC 数据库 写入通话事实表，以 callId 建立唯一索引 request 验签通过 严格防止 Webhook 连续重试造成重复插入流水
10a-c DCC 接入网关 DCC 数据库 意向自动打标与后续任务流转 request 根据 intentGrade 规则判定 A/B级意向直派人工坐席；未接通自动规划下一轮定时呼叫
接口契约要点：话单接收接口必须保证**幂等性**。外部引擎在网络超时情况下会重试推送，DCC 服务端根据 `callId` 查询本地已存在则直接返回 `200 OK`，坚决不二次重复触发后续的意向变更与短信下发。
SEQ-003 · 坐席软电话外呼、通话中记录与确认保存时序 工作台人工操作

展示坐席在【培育任务】工作台【我的任务】发起人工外呼、WebRTC 软电话通话、弹屏填写、通话中草稿每 5 秒暂存、挂机进入话后整理保护锁、跟进提交并置闲的闭环时序。

对应原型：【培育任务】➔【我的任务】+ 软电话工具条 + 客户详情弹屏 参与方：5 个泳道 消息数：14 条交互 重点：通话中防丢草稿 · 挂机话后锁保护 · 状态置闲
# 发送方 接收方 消息 / 接口调用 类型 触发条件 技术实现约束
1-2 【培育任务】工作台 (UI) 软电话通信条 Agent.makeCall(targetPhone) request 坐席点击拨打按钮 校验当前坐席处于空闲状态，号码执行脱敏加密传输
3-4 软电话通信条 【培育任务】工作台 (UI) onCallEstablished 事件回调 event 潜客接听成功 自动滑出录入抽屉，防止坐席忘记记录核心沟通纪要
5-6 【培育任务】工作台 (UI) DCC 后端服务 PUT /api/leads/{id}/follow-up/draft (暂存草稿) request 通话中输入防抖 5 秒自动触发 草稿按坐席工号隔离，意外刷新或掉线重新打开自动回显
7 软电话通信条 【培育任务】工作台 (UI) onCallHungUp 事件回调 event 通话挂断 通信条强制置为 Wrap-up 状态，防止被分配新通话打断填写
8-11 【培育任务】工作台 (UI) DCC 数据库 POST /api/leads/{id}/follow-up/commit request 坐席手动点击确认保存按钮 必填项校验（意向等级、沟通纪要）；事务写入流水
12-14 【培育任务】工作台 (UI) 软电话通信条 Agent.setReady() request 正式提交接口返回 200 自动解除锁定，坐席恢复空闲 Ready 接听状态
前端容灾设计：坐席在通话中记录的文本与选项**同时保存在浏览器 LocalStorage 与服务端草稿表**。即便浏览器意外崩溃或断电，坐席重新登录后点击该线索，系统将精准恢复未提交的内容。
SEQ-004 · ★ 高意向试驾排程预约、定位短信下发与反哺集团CRM闭环时序 ★ 核心转化终态

定义当潜客表达明确到店意向后，坐席在【试驾排程】录入试驾车型、意向门店与排班专属顾问，下发带到店定位指引的短信与企微通知，并将正式试驾工单反哺推送至集团营销 CRM 的全链路闭环时序。

对应原型：【试驾排程】➔【试驾排程工单】+【中台推送监控】+【任务排班】➔【短信模板】 参与方：5 个泳道 消息数：15 条交互 重点：门店顾问日历锁定 · 定位指引短信 · CRM 反哺闭环 · 推送重试补发
# 发送方 接收方 消息 / 接口调用 类型 触发条件 技术实现约束
1-3 【试驾排程】录入端 (UI) DCC 排程引擎 GET /api/testdrive/calendar (查询日历与顾问) request 坐席选定目标门店与意向车系 联动【任务排班】，返回门店可用试驾车配额与在岗顾问时段
4-6 【试驾排程】录入端 (UI) DCC 排程引擎 POST /api/testdrive/booking (创建试驾排程工单) request 坐席点击确认提交排程 事务落库：状态流转为 APPOINTED，锁定线索归属，防止进入公海
7-8 DCC 排程引擎 统一短信/企微网关 POST /api/sms/send-template (下发到店定位短信) event 试驾单成功落库 包含门店真实 GPS 定位导航链接、专属顾问姓名与联系方式
9 DCC 排程引擎 集团营销 CRM POST /crm/open/lead/testdrive-sync (数据反哺) request MQ 异步触发推单 通过 Topic: dcc_crm_sync 发布，携带预约单号、车系、门店编码
10a 集团营销 CRM DCC 排程引擎 HTTP 200 OK { crmOppId: "OPP-9981" } response CRM 校验写入成功 更新试驾单 crm_sync_status=SUCCESS，中台推送监控记录回执
10b 集团营销 CRM DCC 排程引擎 HTTP 500 / Timeout 错误回执 error CRM 宕机或网络抖动 记录重试次数，在中台推送监控大屏展示“失败”，支持一键补发
11-12 DCC 排程引擎 中台推送监控大屏 更新实时指标与推送状态大屏 event 排程闭环完成 刷新预约到店转化漏斗与跨门店履约统计
★ 核心商业价值闭环：【试驾排程】是 DCC 培育链路的核心转化终点。一旦生成排程单，系统立即解除 24h 滞留倒计时威胁并锁定销售归属，同时通过多渠道到店短信与反哺集团营销 CRM，构建起线上培育与线下门店试驾交付的完整闭环。
SEQ-005 · 线索滞留超时告警、自动回收公海与重新分配时序 数据治理与防怠工

展示定时任务巡检、线索滞留阶梯预警（剩余 2 小时企微强催促）、超期 24 小时未跟进强制剥夺归属并回收至【线索管理】公海池、下发客户兜底关怀短信以及触发主管告警通知的完整治理时序。

对应原型：【培育任务】➔【我的任务】(24h滞留倒计时) + 【线索管理】➔【公海池】 参与方：5 个泳道 消息数：14 条交互 重点：两段式阶梯治理 · 企微催促 · 自动清空归属 · 公海重新流转
# 发送方 接收方 消息 / 接口调用 类型 触发条件 技术实现约束
1-3 滞留巡检 Worker DCC 数据库 SELECT * FROM dcc_lead WHERE ... (扫描超时未跟进) request 定时 Worker 轮询 (每10分钟) 走专用只读索引 idx_allocated_followup_status，批量分段处理
4a-5a 滞留治理引擎 企微网关 / 坐席端 POST /wechat/send-warning (发送滞留预警) event 距离最终超时小于 2 小时 通知卡片附带一键拨打直接跳转链接，强化催办效果
4b-5b 滞留治理引擎 DCC 数据库 UPDATE dcc_lead SET owner_id=NULL, status='STAGNANT' error 达到滞留配置阈值 (24 小时未产生通话记录) 清空责任人，写入 dcc_stagnant_log 审计记录，扣减坐席积分
6 滞留治理引擎 统一短信网关 POST /sms/send-template (兜底短信触达) request 配置启用了“滞留自动短信关怀” 检查是否处于夜间勿扰时段，避免违规客诉
7 滞留治理引擎 主管端 推送站内通报与大屏违章角标 event 有线索发生实际滞留回收 计入坐席 KPI 报表，降低后续轮询权重
8 滞留治理引擎 【线索管理】公海池 线索转入公共资源池供重新流转 request 回收成功 支持班长批量指派，或坐席在公海列表主动捞取
业务价值说明：通过严格的滞留超时与两段式（预警 ➔ 强制回收）时序设计，从机制上杜绝销售顾问“占着优质线索不跟进”的怠工行为，保障潜客在黄金 24 小时内必定得到有效触达。
SEQ-006 · 预外呼实时监听、主管耳语指导与通话录音质检抽检时序 运营监控与质检

展示班长在【系统运维 ➔ 预外呼监控】大屏查看在岗通话状态、通过 WebRTC 信令实时旁听坐席对话、发起耳语指导或紧急强拆，以及通话归档后质检员在【统计报表与质检 ➔ 质检管理】调听录音、对照对话文本评分与打标敏感词的完整质控时序。

对应原型：【系统运维】➔【预外呼监控】+【统计报表】➔【质检管理/人工坐席工单】 参与方：5 个泳道 消息数：14 条交互 重点：无感实时监听 · 耳语指导 · OSS 录音归档 · ASR 文本质检
# 发送方 接收方 消息 / 接口调用 类型 触发条件 技术实现约束
1-2 主管端 (UI) 监控与质检服务 GET /api/monitor/agents-live (查询通话列表) request 班长打开【预外呼监控】大屏 WebSocket 或 SSE 每 3 秒推送在岗状态与实时通话时长
3-4 监控与质检服务 WebRTC 通信网关 POST /gateway/call/monitor-listen (发起单向旁听) event 班长点击“实时监听” 仅复制音频流到班长分机，坐席与潜客界面无任何声音或提示
5a 主管端 (UI) WebRTC 通信网关 POST /gateway/call/whisper (耳语指导) request 班长开启耳语功能 网关将班长声音仅混音推流到坐席耳机，潜客端混音静音
5b 主管端 (UI) WebRTC 通信网关 POST /gateway/call/force-hangup (紧急强拆) error 发现严重违规或客诉风险 网关立即发送 SIP BYE 信令，强行终止两端通话并标记强拆日志
6-7 WebRTC 通信网关 录音引擎 (ASR/OSS) 上传录音并调用语音转写 API event 通话正常或异常挂断 生成带有时效校验的 OSS 访问签名；ASR 识别敏感词并标红
8-9 质检主管端 (UI) 监控与质检服务 GET /api/qc/tasks/draw (抽取抽检工单) request 质检员进入【质检管理】 加载录音播放器波形、ASR 转写时间轴、预置质检评分标准卡
10-12 质检主管端 (UI) DCC 数据库 POST /api/qc/evaluations/commit (提交质检打分) request 质检员核验完成点击提交 写入质检事实表，按权重计算综合得分，联动【坐席业绩看板】扣分
质量与合规闭环：通过【预外呼监控】的事中监听/耳语指导，与【质检管理】的事后录音抽检查听，形成覆盖通话全生命周期的质量防线。质检结果直接反哺坐席服务星级，进而影响 7 维度分单规则中的星级加权，促使坐席保持高质量沟通。
